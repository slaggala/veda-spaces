# Catalog V3 media infrastructure: prepared design (not active)

**Status:** prepared for owner acceptance, not activated. Nothing here is deployed or applied.

**Until every control below exists on the target environment, no candidate media is served publicly.** The code
already enforces that:
- `VEDA_CATALOG_MEDIA_DELIVERY_ENABLED` is off by default, and production refuses it.
- Staging and production refuse a catalog without `VEDA_CATALOG_MEDIA_BACKEND=s3`, a bucket, and
  `VEDA_CATALOG_MEDIA_SCANNER=clamd`.

## Source storage

- **Bucket:** one private S3 bucket per environment, for example `veda-catalog-media-staging`.
  - Versioning on.
  - Object Ownership is "bucket owner enforced", so ACLs are disabled.
  - All four Block Public Access settings are on.
  - The bucket policy denies any request that is not TLS and any `PutObject` without `aws:kms` encryption.
- **Encryption:** SSE-KMS with a dedicated customer-managed key, `VEDA_CATALOG_MEDIA_KMS_KEY_ARN`. Key use is
  limited to the API role.
- **Keys:** content hashes only, `source/<sha256>` and `variant/<sha256>`. They are generated by the API and never
  derived from a filename, so no customer data can sit in a key. Uploaded files carry no metadata: images are
  re-encoded and models rewritten.
- **Access:** only the API task role can put, get and delete under `source/` and `variant/`. There is no public
  principal, and no presigned upload URL is issued. Uploads go through the authenticated staff API
  (`catalog.media.edit`), which validates, sanitises and scans before storing.
- **Implementation:** `veda.modules.catalog.media.S3Storage`. It sends `ServerSideEncryption=aws:kms` and sets no
  ACL. It is selected only by `VEDA_CATALOG_MEDIA_BACKEND=s3`.

## Delivery

- **Path:** an approved media hostname, for example `media-staging.vedaspaces.com`, sits in front of the API route
  `/api/v1/public/catalog/media/<sha256>`. The bucket is never exposed.
- **Caching:** responses are `Cache-Control: public, max-age=31536000, immutable`, with `nosniff`,
  `Content-Security-Policy: default-src 'none'; sandbox` and `Cross-Origin-Resource-Policy: cross-origin`. Content-hash
  URLs version the cache, so a change is a new URL.
- **What is served:** only a CLEAN variant that has not been withdrawn or purged and that the ACTIVE release
  references. Anything else gets 404.
- **Site policy:** the public site's Content-Security-Policy gains the media hostname in `img-src` (and `media-src`
  if video is ever approved) on the V3 page only. This is a reviewed change to `_headers`, made when the hostname is
  decided. It is **not** made in this branch.

## Malware scanning

- **Scanner:** ClamAV (`clamd`) as a sidecar, reached at `VEDA_CATALOG_CLAMD_ADDRESS` with the INSTREAM protocol.
  Proposed limits are `StreamMaxLength 30M`, `MaxScanSize 100M`, `MaxFileSize 30M` and `MaxRecursion 10`. Signatures
  are updated by `freshclam`.
- **States:**

  | State | Meaning |
  |---|---|
  | PENDING | Not scanned yet. This is the state with no scanner, outside local and test |
  | CLEAN | Scanned and clean |
  | INFECTED | Refused at upload; nothing is stored |
  | FAILED | The scanner errored; the `catalog-media-scan` job retries |

- **Fail closed:** release validation refuses any media that is not CLEAN, and delivery serves only CLEAN.

## Lifecycle and deletion

- **Withdrawal:** a deletion request or withdrawn consent (`POST /api/v1/catalog/media/<sha>/withdraw`, reason
  required) deletes the bytes of the source and every variant at once and keeps the hashes. Manifests stay intact,
  nothing is served, and new releases naming the media fail validation.
- **Unreferenced sources:** sources no live media record names are purged after `VEDA_CATALOG_MEDIA_RETENTION_DAYS`
  (default 180) by the `catalog-media-retention` job.
- **Bucket rule:** an S3 lifecycle rule expires noncurrent versions after 30 days, so deleted bytes do not survive
  in old versions beyond that window. The window needs the owner's decision.
- **Audit:** every upload, scan, withdrawal and purge is a catalog event, and media rows are audited.

## Rights and consent

Each media record carries:
- the owner, licence, usage (`owned`, `licensed` or `client_permission`) and expiry;
- for a client's photograph, a `consent_reference` to the client's written permission.

Release validation refuses expired rights. Withdrawing consent uses the withdrawal path above.
