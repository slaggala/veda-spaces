# 03 — Database Architecture and Foundational Schema

Governing decisions: [ADR-001](decisions/ADR-001-app-user-table.md) · [ADR-002](decisions/ADR-002-uuidv7-identifiers.md) · [ADR-003](decisions/ADR-003-audit-contract.md) · [ADR-004](decisions/ADR-004-security-event-log.md) · [ADR-006](decisions/ADR-006-mfa-policy.md)

## 1. Conventions

> Traces: DATA-010

| Topic | Convention |
|---|---|
| Table names | Singular snake_case (`lead`, `user_role`). The **User** entity's physical table is **`app_user`** (ADR-001). No physical table named `user` may exist. The ORM model class may be named `User`. |
| Column names | snake_case. FK columns are `<referenced_entity>_id`, except the contract actor columns (`created_by`, `updated_by`, `deleted_by`) and semantic names (`assigned_to`, `recipient_user_id`). |
| Logical types | `GUID` · `UTCDATETIME` · `BOOL` · `JSON` · `CODE(n)` · `MONEY_MINOR`. Physical mapping per engine is in §12. |
| Enumerations | `CODE(n)` = string plus `CHECK (col IN (...))`. Native ENUM types are never used. |
| Money | `MONEY_MINOR` = BIGINT integer minor units (paise), plus `currency CHAR(3)` (ISO 4217, default `INR`). Floating point is never used for money (DATA-016). |
| Index names | `ix_<table>__<cols>`, unique `ux_<table>__<cols>`, check `ck_<table>__<rule>`, FK `fk_<table>__<col>` |
| FK behavior | `ON DELETE RESTRICT` everywhere. Records are soft-deleted, so cascades are never used. |
| SQLite connection pragmas | `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`, `synchronous=NORMAL`, applied on every connection and verified at startup |
| Partial index predicate | Written as `WHERE is_deleted = false`. Rendered per engine (§12). |

## 2. The audit contract (ADR-003)

### 2.1 Columns

> Traces: DATA-001, DATA-003, DATA-004, DATA-005, DATA-006

Every persisted table starts with these nine columns: domain, security, junction, configuration, reference, log and business tables alike. **No table omits a column.** The exception registry (§2.9) can only relax *behavior* (for example "never soft-deleted"), never remove a column.

| # | Column | Logical type | Null | Default | Rules |
|---|---|---|---|---|---|
| 1 | `id` | GUID | NOT NULL | UUIDv7 generated by the service layer | Primary key. Immutable. |
| 2 | `created_on` | UTCDATETIME | NOT NULL | Transaction clock | Set once on insert. Never accepted from clients. |
| 3 | `updated_on` | UTCDATETIME | NOT NULL | = `created_on` | Set on every update |
| 4 | `created_by` | GUID | NOT NULL | Actor | **FK → `app_user.id`**. Immutable. |
| 5 | `updated_by` | GUID | NOT NULL | Actor | **FK → `app_user.id`** |
| 6 | `is_deleted` | BOOL | NOT NULL | false | Soft-delete flag |
| 7 | `deleted_on` | UTCDATETIME | NULL | — | Set together with `is_deleted` |
| 8 | `deleted_by` | GUID | NULL | — | **FK → `app_user.id`** |
| 9 | `version` | INTEGER | NOT NULL | 1 | Incremented on every update. Used for optimistic concurrency. |

**Contract constraints** (on every table):

| Constraint | Rule |
|---|---|
| `ck_<t>__soft_delete_consistent` | `(is_deleted = false AND deleted_on IS NULL AND deleted_by IS NULL) OR (is_deleted = true AND deleted_on IS NOT NULL AND deleted_by IS NOT NULL)` |
| `ck_<t>__version_positive` | `version >= 1` |
| `ck_<t>__updated_after_created` | `updated_on >= created_on` |
| `ck_<t>__id_format` | `id` is canonical UUIDv7 text (SQLite, §12). On PostgreSQL the native `uuid` type enforces format, and the version nibble is checked by the kernel type. |
| `fk_<t>__created_by`, `fk_<t>__updated_by`, `fk_<t>__deleted_by` | → `app_user.id` ON DELETE RESTRICT |

### 2.2 Identifiers (ADR-002, DATA-002, DATA-012, DATA-013)

| Aspect | Rule |
|---|---|
| Algorithm | UUID version 7 (RFC 9562): 48-bit Unix-millisecond timestamp, then version `7`, variant `10`, then random bits |
| Generation | Service layer, before insert. Never generated by the database. There are no integer IDs, no auto-increment, and no DB sequence values are exposed. |
| Canonical external form | Exactly 32 lowercase hex characters, no hyphens, for example `0192a4f1c3b27e8d9f10a2b3c4d5e6f7` |
| Validation pattern | `^[0-9a-f]{12}7[0-9a-f]{3}[89ab][0-9a-f]{15}$` (checks the version and variant nibbles). Anything else is rejected at the API boundary with `422 INVALID_ID` (08 §2.2). |
| Immutability | `id` is never updated. The kernel raises if an `id` attribute becomes dirty. |
| SQLite storage | `CHAR(32)` in the canonical form, with `ck_<t>__id_format` |
| PostgreSQL storage | Native `uuid` (16 bytes). The kernel `GUID` type converts canonical 32-hex ↔ `uuid` on bind and result, so application code, APIs and JSON payloads only ever see the 32-hex form (§12). |
| Ordering | UUIDv7 sorts approximately by creation time. Lists use explicit sort keys (`created_on`, `id` as tie-breaker), never implicit id order. |
| Human-readable numbers | Business numbers such as `lead_number` come from `number_sequence` (§6.3). They are internal display values only: never used as identifiers in API paths and never shown on public surfaces (ADR-002, LEAD-025). |

**Time.** All values are UTC. One clock reading per transaction (§2.8). The UI converts to the user's `timezone` (PLAT-007).

### 2.3 Actor columns and seeded system users (DATA-004, USER-005)

- `created_by`, `updated_by` and `deleted_by` always come from the **actor context**. Request payloads never supply them.
- They are **database-enforced foreign keys** to `app_user.id`, and `created_by` / `updated_by` are NOT NULL.
- Non-human writers are seeded `app_user` rows with `user_type = 'SYSTEM'`. They have no `user_credential`, and login rejects `user_type <> 'HUMAN'`.

| Seeded system user | Fixed id (valid UUIDv7 form, timestamp 0) | Actor for |
|---|---|---|
| SYSTEM | `00000000000070008000000000000001` | Migrations, seeding, scheduled jobs, outbox worker, retention jobs |
| WEB_INTAKE | `00000000000070008000000000000002` | Leads created through the public website form |
| ANONYMOUS | `00000000000070008000000000000003` | Security events caused by unauthenticated requests (failed logins for unknown emails, password-reset requests, blocked public submissions) |

**Bootstrap.**

- The `SYSTEM` row references itself (`created_by = updated_by = id`). Both engines accept this in a single-row insert, because FK checks run at statement end.
- WEB_INTAKE and ANONYMOUS rows are then created by SYSTEM in the same migration.

**Locking note (PostgreSQL).** FK checks take `FOR KEY SHARE` locks on the referenced `app_user` row. These are compatible with each other and with `FOR NO KEY UPDATE`, which profile updates take, so the many rows referencing SYSTEM do not contend.

### 2.4 Soft delete (DATA-005, DATA-008, DATA-009)

- A delete in the API is a soft delete: it sets `is_deleted = true`, `deleted_on` and `deleted_by`, and writes an audit row with action `DELETE`. Restore reverses it (`RESTORE`).
- Repositories apply `is_deleted = false` by default (a global ORM loader criterion). Opting out requires an explicit `include_deleted` flag, which the API exposes only to holders of the resource's `*.restore` permission.
- Hard delete happens only in:
  - the retention and erasure procedures (07 §8);
  - tables listed in the exception registry (§2.9).

  Each hard delete writes a summary audit or security event.

### 2.5 Optimistic concurrency (DATA-006)

- `version` is the ORM version counter. Every UPDATE includes `WHERE id = :id AND version = :expected`. If zero rows are affected, the response is `409 VERSION_CONFLICT`.
- The API exposes `version` as the `ETag` and requires it in `If-Match` (API-006).

### 2.6 Uniqueness under soft delete (DATA-007)

Business-key uniqueness applies only among live rows, through partial unique indexes (`… WHERE is_deleted = false`). A soft-deleted user's email can be reused. A restore that would collide fails with `409 DUPLICATE`.

### 2.7 Schema conformance check (DATA-011, DATA-014)

A CI job migrates an empty database on **both** SQLite and PostgreSQL, introspects the schema, and fails the build when any table:

1. lacks any of the nine contract columns, or has the wrong logical type or nullability;
2. has a primary key other than `id` of the GUID type;
3. lacks the three actor FKs to `app_user.id`;
4. has a column ending in `_id`, or an actor column, whose type is not the GUID type (checked for every FK, DATA-012);
5. has a unique index on business columns without the `is_deleted = false` predicate, unless allow-listed in §2.9;
6. has an FK with a cascade action, or uses a native ENUM type;
7. is not registered in the audit policy registry (07 §2);
8. is named `user` in any schema (ADR-001);
9. has a behavioral deviation (no soft delete, hard-delete purge, immutable rows) that is not listed in the exception registry (§2.9).

### 2.8 Population and transactional atomicity (ADR-003, DATA-015)

> Traces: DATA-003

Audit fields are populated by the platform kernel. They are never set by services, repositories or clients. All writes for one business operation share one database transaction.

```
API request / job
  │ 1. ActorContext established (user id from verified JWT, or a seeded system user) — no actor → request fails
  │ 2. Service opens ONE unit of work (SQLAlchemy Session; SQLite: BEGIN IMMEDIATE for write transactions)
  │ 3. Service mutates ORM objects (insert / modify / soft-delete helper)
  │ 4. session.flush() → kernel before_flush hook, per affected object:
  │      tx_time      = the single clock reading captured when the unit of work began
  │      INSERT       → id (UUIDv7 if absent), created_on = updated_on = tx_time,
  │                     created_by = updated_by = actor, version = 1, is_deleted = false
  │      UPDATE       → updated_on = tx_time, updated_by = actor, version = version + 1 (ORM version counter)
  │      SOFT DELETE  → is_deleted = true, deleted_on = tx_time, deleted_by = actor (+ UPDATE stamping)
  │      audit_log rows added to the same session (07 §3)
  │ 5. outbox_event rows added by the service in the same session (02 §10)
  │ 6. COMMIT → business rows + contract columns + audit_log rows + outbox rows commit together, or none do
  └ 7. Any exception before commit → ROLLBACK of everything (the audit write cannot outlive or miss the change)
```

- `BEGIN IMMEDIATE` on SQLite takes the write lock at the start of a write unit of work. This avoids the deadlock-prone read-to-write lock upgrade under concurrency. PostgreSQL uses the default `READ COMMITTED` together with optimistic `version` checks.
- **Security events** (05 §9) follow two paths:
  - When they accompany a successful business change (for example a session created at login), they are written in the same transaction.
  - When they record a failure or denial that rolls back or has no business change (login failure, permission denied), they are written in a **separate** short transaction, so the evidence survives the rollback (SEVT-011).
- **Email and other external side effects** never run inside the transaction. They are drained from the outbox after commit, so a delivery failure cannot roll back a persisted lead (NOTIF-008).

### 2.9 Contract exception registry (DATA-014)

> Traces: AUDIT-004

Every behavioral exception to the contract is listed here. The conformance check reads this registry. Columns are never exempt.

| ID | Table(s) | Exception | Justification | Compensating control |
|---|---|---|---|---|
| EXC-001 | `audit_log`, `security_event_log` | Rows are immutable: never updated or soft-deleted. `updated_on = created_on`, `updated_by = created_by`, `version = 1`, `is_deleted = false` for life. | They are the evidence stores. Mutation would defeat their purpose. | DB triggers/grants block UPDATE/DELETE (07 §6). The hash chain covers `security_event_log` (SEVT-006). |
| EXC-002 | `audit_log`, `security_event_log` | Hard-deleted by the retention job after archival | Configurable retention (SEVT-004, AUDIT-009) | Archive to S3 with checksum verification before delete. A summary event is written. |
| EXC-003 | `refresh_token`, `mfa_challenge` | Hard-deleted by purge after expiry, never soft-deleted | Short-lived secrets-derived rows. Keeping them adds risk and no value. | Lifecycle events are in `security_event_log`. Purge runs as SYSTEM with a summary event. |
| EXC-004 | `outbox_event` | DONE rows hard-deleted after the configured retention | Operational queue, not business data | Business effect is audited in `audit_log`. DEAD rows are retained until resolved. |
| EXC-005 | `notification` | Hard-deleted after the configured retention once read | User inbox convenience data | Source event traceable via `source_event_id` until purge |
| EXC-006 | `user_session`, `password_reset_token`, `user_mfa_recovery_code` | Never soft-deleted. The lifecycle uses `revoked_on`, `used_on` and `invalidated_on`. | These states are more precise than a generic delete flag | Lifecycle transitions write security events |
| EXC-007 | Token-hash and chain columns (`refresh_token.token_hash`, `password_reset_token.token_hash`, `mfa_challenge.token_hash`, `user_mfa_recovery_code.code_hash`, `security_event_log.chain_seq`) | Unique index **without** the `is_deleted` predicate | Hashes and chain positions must be globally unique | — |
| EXC-008 | `app_user` rows SYSTEM, WEB_INTAKE, ANONYMOUS | Cannot be soft-deleted, disabled or given credentials | Required actors for FK integrity | Service guard plus seed migration check |

- **Audit:** FULL. `last_login_on` and `authz_version` are excluded from diffs.

## 12. SQLite and PostgreSQL mapping (DATA-012, PLAT-004)

> Traces: DATA-010, DATA-016

The kernel defines each logical type once. Engine-specific DDL is generated by SQLAlchemy dialects and Alembic.

| Logical type | SQLite (MVP) | PostgreSQL (migration target) | Application / API form |
|---|---|---|---|
| `GUID` | `CHAR(32)` + `CHECK (length(col)=32 AND col NOT GLOB '*[^0-9a-f]*' AND substr(col,13,1)='7' AND substr(col,17,1) IN ('8','9','a','b'))` | Native `uuid`. The kernel type validates the version-7 nibble on bind. | 32 lowercase hex string |
| `UTCDATETIME` | `TEXT` fixed-width `YYYY-MM-DDTHH:MM:SS.ffffffZ` (lexicographically sortable) | `timestamptz` | RFC 3339 UTC `…Z` |
| `DATE` | `TEXT` `YYYY-MM-DD` | `date` | `YYYY-MM-DD` |
| `BOOL` | `INTEGER` + `CHECK (col IN (0,1))` | `boolean` | JSON boolean |
| `JSON` | `TEXT` + `CHECK (json_valid(col))` (JSON1) | `jsonb` | JSON |
| `VARCHAR(n)` / `CHAR(n)` | `TEXT` affinity + generated `CHECK (length(col) <= n)`, because SQLite does not enforce declared lengths | `varchar(n)` / `char(n)` | string |
| `TEXT` | `TEXT` | `text` | string |
| `CODE(n)` | `TEXT` + length and `IN (…)` CHECKs | `varchar(n)` + `IN (…)` CHECK | string |
| `INTEGER` / `SMALLINT` / `BIGINT` | `INTEGER` | `integer` / `smallint` / `bigint` | JSON number |
| `MONEY_MINOR` | `INTEGER` (64-bit) | `bigint` | Decimal string + currency (08 §2.2) |
| Partial index predicate | `WHERE is_deleted = 0` | `WHERE is_deleted = false` | — |
| Case-insensitive match | `lower(col) LIKE lower(:q)` | Same expression, then `pg_trgm` GIN (11 §3) | — |
| Immutability guard | `BEFORE UPDATE/DELETE` triggers `RAISE(ABORT)` | Grants (INSERT, SELECT only) + triggers | — |
| `UPDATE … RETURNING` | SQLite ≥ 3.35 (startup check) | Native | — |

The data migration of `GUID` columns converts `CHAR(32)` text to `uuid` with `CAST(col AS uuid)`. PostgreSQL accepts the unhyphenated 32-hex input form. The copy is verified row by row with checksums in the migration runbook (11 §3.4).
